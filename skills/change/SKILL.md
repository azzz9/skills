# Change

## いつ使うか

- 直す方法が分かっていて、これからコードを変えるとき。
- 新規にファイルや機能を作るとき。
- 編集や追加の前に `design` を通す。設計が決まっていても、方針と shape を確認する。
- 複数 phase なら `plan`、原因が分からないなら `diagnose`、調べるだけなら `understand`。

## モード

選び方: 必ず1つ。`add` と `reshape` は排他。

- **add**: 新しい動きを足す、または新規に作る（例: 機能追加、新規ファイル）。データの形を先に決める。既存の repo ならテストを先に書く。新規なら最小の scaffold を作り、動く証拠を先に決める。分岐が増えるなら、状態機械か表にする。成功の証拠は、既存なら failing test → passing、新規なら scaffold 上の test か run。
- **reshape**: 動きを変えずに構造を変える（例: リファクタ、名前変更、分割）。呼び出し元をすべて同じ wave で移し、古い API を消す。互換用の残しを置かない。成功の証拠は、今の動きを記録したテストが変更前も変更後も通ること。

## 共通ルール

- 作る前、変える前に、どうなったら成功かを決める。決めずに書き始めない。
- 編集の前に `design` を通し、`## 方針` を出す。小さい修正は2から3行でよい。
- 実際の画面、実行結果、artifact で確かめる。テストだけ、目視だけでは足りない。判定できない、または違う画面で試したなら合格にしない。
- コメントの基準は `../shared/references/comments.md`。

## 委譲

呼び出し元の pi が `subagent` を呼ぶ。形と agent の一覧は `../shared/references/delegation.md`。

`standard` に渡す:

- 対象が複数ファイル、または同じ形の編集が繰り返す。
- scope と成功条件が先に決まっていて、呼び出し元の文脈をあまり必要としない。
- 呼び出し元の context が混んでいて、実装を分けたい。
- 独立した変更を並列に走らせたい。

呼び出し元が自分でやる（inherit）:

- 1から2ファイル、数行で、文脈がすでに手元にある。
- 設計や検証と往復しながら直す必要がある。
- 変更が難しく、呼び出し元のモデルと文脈が要る。
- 委譲の brief と review の手間が、変更そのものより大きい。

scope がまだ固まっていないなら `intent` に渡すか、`design` に戻る。どちらの場合も、brief に対象、成功条件、触らないもの、報告の形を書き、diff は呼び出し元が読む。子の自己申告を信じない。

## 終わり

この review のスコープは今回の変更の diff だけ。PR の差分全体は `ship` が review する。

1. 検証する。
2. 今回の変更の diff だけを `review` の slop と comments に通す。
3. 大きい変更、設計判断、またはユーザーが求めたなら、今回の変更の diff を `review` の code モードに通す。code モードは `reviewer` を lane ごとに使う。
4. findings は直すか、直さない理由を書く。
5. commit と PR は `ship` に渡す。

## 停止

- 設計判断が必要なら `design` に戻る。
- 原因が不明な不具合なら `diagnose` に渡す。
- 検証できないなら、できない理由を書いて止まる。
